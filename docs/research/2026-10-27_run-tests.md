# run_tests, and the pytest option that deletes folders - 2026-10-27

## Objective

Build `run_tests`, the first Phase 2 extension. It runs a repo's tests on CPU and reports only the failures, each marked as new or as already failing when the agent started, so the agent neither drowns in pytest logs nor "fixes" failures it didn't cause.

## Process

### Step 1: the shape of the tool

- One tool, two parameters: `paths` (test files, folders or ids) and an optional time limit. Every token of a tool description is paid on every turn, so the description is one sentence.
- Results come from pytest's JUnit XML, not from parsing its text output.
- Runs are CPU-only: `LUTHI_ALLOW_CPU=1`, and the CUDA, HIP and ROCm devices hidden.

### Step 2: the "already failing" baseline

- **First idea:** run the whole suite at session start. Too slow, since LuthiModel's suite takes many minutes on CPU.
- **What was built:**
  - At session start, record the state with `git stash create`. It captures uncommitted tracked changes as a commit object and changes nothing in the working tree.
  - Only when tests fail, run those test files once at that state, in a temporary worktree, then remove it.
  - Results are cached per file for the session.
- **The baseline worktree needs a Python environment.** `uv run` in a temp folder has no project environment, and would create an empty one. So the interpreter is resolved once from the real checkout and reused for both runs.
- **The baseline worktree gets its own compiled-extension cache.** This is the LuthiModel lesson from the eval build, step 5: two checkouts sharing one cache load each other's builds.

### Step 3: the import trap again

- In the eval build (step 11), tests in one checkout silently imported missing modules from another, through an editable install of a namespace package. On Brian's machine both repos are installed editable, so a baseline worktree would do the same: a test missing its module at the start could import the agent's new module from the real checkout and be mislabeled.
- **Fix:** run pytest through a short Python bootstrap. It removes editable-install finders, their path hooks, and the folders their `.pth` files add, then puts the checkout under test first.
- **Test:** a namespace package installed editable from checkout A, and checkout B missing one module.
  - Plain pytest in B passes, importing the module from A. That control shows the leak is real.
  - Through the bootstrap, the module stays missing.

### Step 4: options are refused, and why

- **pytest options are refused** (`-p`, `--basetemp`, and the rest). One reason is that options aren't test targets. The other matters more: `--basetemp` deletes the folder it names.
- **That claim was checked, and the first check was misleading.** `pytest --basetemp=keep` with a trivial test left `keep/charter.md` alone. pytest only clears the folder when a test asks for a temporary directory. With one test using `tmp_path`, the file was gone.
- **What it means for the guard:** the guard allowed `pytest --basetemp=data/identity`, because pytest isn't a file command. Sanctuary's tests use `tmp_path` everywhere, so that one command would have deleted the charter.
  - The guard now treats paths named by write-or-wipe options the way it treats any write (`docs/decisions.md`, 2026-10-27).
  - The tests failed first, and passed after the change.

### Step 5: the guard and the tool together

- **The conflict:** the guard checks custom tools' path-like arguments as write targets. So `run_tests` on `sanctuary/tests/identity/test_charter.py` would have been blocked, and the agent's rule says to stop after a block. A false block would end its work.
- **Fix:** the tool declares itself read-only to the guard. It accepts only targets inside the repo and no options, so it is narrower than `pytest` through bash, which the guard allows.

### Step 6: real repos

On eval worktrees, with no Pi involved:
- **Sanctuary:** the identity tests ran, 16 passed.
- **LuthiModel:** `test_backend_declaration.py` has one test that fails on CPU by design. `run_tests` reported it as "already failing before you started, not caused by your changes", which is exactly the case it was built for.

## Conclusion

- **Built and tested without the model:**
  - 12 unit and integration tests, including the import leak and its control;
  - 5 checks inside real Pi alongside the guard;
  - 30 guard tests, 2 of them new.
- **Not installed for everyday use:** `install-config.bat` now installs only the guard until an extension has earned its place in the eval.

**Open:**
- Whether `run_tests` helps the agent, measured against the baseline on its own claim: fewer turns and tokens spent on test output, and fewer edits aimed at failures that were already there.
- Whether `--timeout=120` per test suits Sanctuary on Brian's CPU.
- The guard's new option rule needs the cross-family review, with the rest of the guard.
